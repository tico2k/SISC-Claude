# 소명프로세스 (Clarification Process) 가이드

이 문서는 **Fleit InsiderGuard** 시스템에서 보안 위협 탐지부터 소명 종결까지의 전체 프로세스를 설명합니다.

---

## 1. 개요

소명프로세스는 SIEM(Sentinel, ELK 등)에서 탐지된 이상 행위에 대해 관련 임직원에게 사유를 확인하고, 보안 부서에서 이를 검토하여 조치하는 일련의 과정을 의미합니다. 이를 통해 오탐을 줄이고 실질적인 정보 유출 위협에 집중할 수 있습니다.

### 주요 특징

- 📧 **자동 알림 시스템**: 케이스 생성, 검토 완료, 마감 임박 시 자동 이메일 발송
- 📊 **투명한 이력 관리**: 모든 상태 변경과 검토 의견이 기록됩니다
- ⏰ **동적 마감일 관리**: DB 기반 스케줄링으로 관리자가 언제든 마감 알림 시간을 동적으로 조절 가능
- 🔒 **동시 검토 방지**: Case Locking 기능으로 복수 관리자의 중복 검토 방지
- 🔐 **역할별 철저한 데이터 격리 (RBAC)**: 일반 사용자는 승인 전/종결된 내부 보안 건을 볼 수 없도록 차단
- ⚖️ **반려 3대 분기 워크플로우**: 단순 반려를 넘어 재소명(A), 보안교육/서약(B), 징계/감사이관(C) 지원
- 🖨️ **감사 이관 보고서 원클릭 인쇄**: 중대 위반건 이관 시 즉시 활용 가능한 공문 양식 출력
- 🌐 **완벽한 다국어(i18n) 지원**: 한국어/영어 전 화면 지원 및 보안 용어(Medium) 표준화

## 3. 단계별 상세 설명

### 1단계: 탐지 및 케이스 생성 (Detection)

- **주체**: SIEM & Collector 또는 보안 관리자 수동 생성
- **내용**: SIEM에서 발생한 보안 이벤트를 기반으로 시스템 내에 케이스를 생성합니다.
- **결과**: `미확인 (UNCLASSIFIED)` 상태의 신규 케이스가 생성됩니다.
- **보안 격리**: 일반 임직원은 아직 검토되지 않은 `미확인` 건을 절대 열람할 수 없습니다 (관리자 전용).

### 2단계: 보안관리자 초기 검토 (Initial Review)

- **주체**: 보안관리자 (SECURITY_ADMIN, SYSTEM_ADMIN)
- **내용**: 탐지된 로그와 컨텐츠를 확인하여 실제 소명이 필요한 건인지 일차 통제합니다.
- **보안 잠금 (Case Locking)**:
  - 관리자가 상세 화면에 진입하면 해당 케이스에 **Lock**이 걸려 타 관리자의 중복 검토/오조작을 방지합니다.
- **분기**:
  - **오탐/정상**: 소명 요청 없이 케이스를 즉시 종결 처리합니다 (`종결 (CLOSE)`).
  - **소명 요청**: 관련 임직원에게 소명을 요청합니다 (`요청 (REQUEST)`).
    - 케이스 제출 마감일 설정 및 소명 요청 안내 이메일 발송
    - 이 시점부터 대상 임직원의 '나의 소명 관리' 목록에 케이스가 노출됩니다.

### 3단계: 마감일 관리 (Deadline Management)

- **주체**: 백엔드 내장형 스케줄러 (APScheduler - DB 동기화)
- **자동 알림**: 매일 아침 미제출(`REQUEST`, `REJECT` 상태) 케이스를 검사하여 마감 3일 전, 1일 전에 독려 메일을 발송합니다.

### 4단계: 일반 임직원 소명 프로세스 (Employee Clarification)

- **주체**: 피소명자 (일반 임직원, USER)
- **UI/UX 최적화**:
  - **나의 소명 관리**: 본인에게 배정된 케이스만 조회되며, 불필요한 '대상자 이름' 필터는 제거되어 직관적입니다.
  - **다이렉트 진입**: 대시보드에서 본인의 사건 행을 클릭하면 검토 화면을 거치지 않고 직접 작성 페이지(`/cases/{id}`)로 즉시 이동합니다.
  - **스마트 네비게이션**: 상단 '대시보드로 돌아가기' 버튼을 통해 이전 문맥을 유지하며 손쉽게 복귀 가능합니다.
- **작성 및 제출**: 업무 연관성 및 정당 사유를 기재하고 증빙 파일(최대 10MB, 확장자 무결성 검증)을 첨부하여 제출합니다.
- **결과**: 케이스 상태가 `제출 (SUBMIT)`로 승급되며 담당 관리자에게 알림이 전송됩니다.

### 5단계: 심의 및 반려 3대 워크플로우 (Final Review & Rejection Subtypes)

- **주체**: 보안팀 / 감사팀 (SECURITY_ADMIN, AUDIT_TEAM, SYSTEM_ADMIN)
- **승인 (APPROVE)**:
  - 소명 사유가 타당하다고 판단될 경우 승인 처리하며, 케이스 결과(정당 사유)를 기록하고 직원에게 통보합니다.
- **반려 (REJECT) - 3대 후속 조치 분기**:
  보안 관리자는 단순 반려 외에 기업 보안 규정에 따라 3가지 명확한 후속 조치를 선택하여 처리합니다:
  
  1. **유형 A (소명 불충분 - 재소명 요구)**:
     - 증빙이나 소명 내용이 불충분한 경우, 보완 사유를 고지하고 재소명 기회를 부여합니다.
     - 직원은 다시 4단계로 돌아가 내용을 보완하여 재제출합니다.
  2. **유형 B (경미한 규정 위반 - 보안 교육 및 서약서 징구)**:
     - 의도치 않은 단순 실수 또는 경미한 내규 위반인 경우, 온라인 보안 교육 이수 및 보안 서약서 작성을 안내하며 사후 조치 후 종결합니다.
  3. **유형 C (중대 위반 의심 - 징계 요청 및 감사팀 공식 이관)**:
     - 고의적 정보 유출, 대량 반출 등 중대 위반 건에 대해 소명을 기각하고 사내 감사팀/인사위원회로 공식 징계 절차를 이관합니다.
     - **인쇄용 보안 감사 보고서(Audit Escalation Report) 발행**:
       - '감사 이관 보고서 인쇄' 버튼을 클릭하여 사건 개요, 탐지 로그, 임직원 제출 내역, 보안팀 심의 의견이 완벽히 정리된 표준 공문서 양식 팝업을 즉시 호출하고 인쇄/PDF 저장을 수행할 수 있습니다.

### 6단계: 최종 종결 (Closure)

- **주체**: 관리자 또는 시스템
- **내용**: 승인 완료(`APPROVE`)되었거나 사후 조치(교육/서약 완료, 감사 이관 등)가 끝난 건을 최종 `종결 (CLOSE)` 처리합니다.
- **격리 보장**: 종결된 건은 일반 사용자에게 노출되지 않으며, 관리자 통계에 영구 보존됩니다.

## 4. 케이스 진행 상태 (Status) 및 가시성 매트릭스

| 상태명 | 시스템 코드 | 일반 사용자(USER) 노출 여부 | 설명 |
| :--- | :--- | :---: | :--- |
| **미확인** | `UNCLASSIFIED` | ❌ **은닉 (보안 격리)** | SIEM 수집 직후 초기 상태 (관리자만 검토) |
| **요청** | `REQUEST` | ✅ **노출** | 위험도 식별 후 직원에게 소명을 정식 요청한 상태 |
| **제출** | `SUBMIT` | ✅ **노출** | 직원이 소명서와 증빙을 제출하여 검토 대기 중인 상태 |
| **승인** | `APPROVE` | ✅ **노출** | 검토자가 소명을 타당하다고 승인 완료한 상태 |
| **반려** | `REJECT` | ✅ **노출** | 사유 불충분, 교육 서약, 또는 징계 이관 통보 상태 |
| **종결** | `CLOSE` | ❌ **은닉 (보안 격리)** | 사후 조치까지 모두 끝난 최종 마감 상태 |

> 💡 **다중 상태(OR) 필터 기능**: 목록 상단의 상태 뱃지 버튼을 여러 개 동시 선택(예: `[요청]` + `[반려]`)하여 복합 상태 케이스를 한눈에 모아볼 수 있으며, 초기화 버튼(🔄)을 통해 1초 만에 전체 조회로 복원할 수 있습니다.

### 상태 전이 규칙 (서버 강제)

규칙은 `backend/modules/cases/services.py`에 모여 있으며, 허용되지 않는 작업은 API가 거부합니다.

| 작업 (API) | 허용되는 현재 상태 | 결과 상태 | 위반 시 |
| :--- | :--- | :--- | :--- |
| 소명 요청 (`POST /cases/{id}/request`) | 미확인 | 요청 | 409 |
| 소명 제출 (`POST /submissions`) | 요청, 반려 A(소명 불충분) | 제출 | 409 (본인의 미확인·종결 건은 403) |
| 심의 (`POST /reviews`) | 제출 | 승인 또는 반려 | 409 |
| 종결 (`POST /cases/{id}/close`) | 종결을 제외한 모든 상태 | 종결 | 409 |

- **심의 결과 조합**: 승인은 `정당 사유`·`경미한 위반`, 반려는 `소명 불충분`(A)·`교육 필요`(B)·`징계 요청`(C)만 허용합니다. 그 외 조합이나 심의로 `종결`·`요청`을 지정하면 422를 반환합니다.
- **Case Lock**: 다른 관리자가 잠근 케이스(30분 이내)는 요청·심의·종결이 거부(409)됩니다. 잠금은 30분이 지나면 무시됩니다.
- **첨부 다운로드**: 일반 사용자는 본인 케이스라도 미확인·종결 상태이면 다운로드할 수 없습니다(403).
- **감사 로그**: 케이스 생성·요청·제출·심의·종결 시 `SystemAuditLog`에 `CASE_CREATED`, `CASE_REQUESTED`, `CASE_SUBMITTED`, `CASE_REVIEWED`, `CASE_CLOSED`가 기록됩니다.

## 5. 단계별 알림 (Email Notifications)

SICS 시스템은 비동기 작업(FastAPI BackgroundTasks, APScheduler)을 통해 지연 없이 담당자에게 알림을 발송합니다.

| 트리거 이벤트 | 기본 수신자 | 메일 요지 |
|--------|--------|------|
| **케이스 생성** | 보안 관리자 | 신규 SIEM 보안 이벤트 수집 및 케이스 생성 통보 |
| **소명 요청 발송**| 피소명 직원 | 상세 사건 고지 및 제출 기한(마감일) 안내 |
| **마감 임박(3/1일전)**| 피소명 직원 | 미처리 소명 건 제출 독려 (매일 아침 자동 스케줄링) |
| **소명서 제출** | 보안 관리자 | 할당된 임직원이 소명서(증빙) 작성을 완료했음을 알림 |
| **검토 완료/심의**| 피소명 직원 | 최종 심의에 따른 승인, 반려 사유(A/B/C 유형) 통보 |
